# Adapter package starter prompts

Use one prompt per separate package chat after Stage 20. The prompts create separate adapters; they do not change the core package. Each chat should inspect the current `Workes.ConsoleSystem` API and the Project Formula before scaffolding.

## Shared instructions for each package chat

- Work in `C:\GitHub Repos\C# Package Dev` and use the Project Formula at `C:\GitHub Repos\C# Package Dev\Project Formula`. Read `PROJECT_FORMULA_USAGE.txt` and `PACKAGE_RELEASE_CHECKLIST.txt` before starting.
- Create the package with `create-package.ps1`; do not hand-build a competing scaffold. Use the latest published `Workes.ConsoleSystem` version. If Stage 20's version is not published yet, use only APIs present in the latest published version and do not reference an unpublished package version.
- Keep the adapter independent of ConsoleSystem internals. Do not add Unity, Godot, or provider-specific dependencies to the core package.
- Give the adapter a sensible built-in severity mapping and let consumers override it. An intentionally ignored or unmapped provider level creates no ConsoleSystem entry.
- Use `LogEntry` and `ConsoleManager.RecordEntry` when available and useful source/exception metadata is available. Do not introduce a generic bridge into the core.
- Build, test, document, inspect the package, and make the initial local commit on `main` after the package is ready. Use `setup-github-repository.ps1 -CreateRemote` for a public repository under `WorkesLibraries`; omit `-Push`. The user will push. Do not create `release` branches.
- Ask the user only for product decisions that cannot be resolved from the package formula, target framework, platform APIs, or the current ConsoleSystem docs. Do not silently claim compatibility with unverified engine versions.

## Unity: `Workes.ConsoleSystem.Unity`

> Create a Unity logging adapter package named `Workes.ConsoleSystem.Unity` in `C:\GitHub Repos\C# Package Dev\Workes.ConsoleSystem.Unity`. Follow the shared adapter instructions above and the Project Formula. Inspect the current Unity logging callback APIs and available Unity package conventions, then implement an opt-in disposable attachment that forwards Unity log callbacks to a supplied `ConsoleManager`. Map Unity severities to ConsoleSystem `LogLevel` with a usable default and a consumer customization point; allow selected source severities to be ignored. Preserve the Unity log message, include the Unity context/object as source metadata when useful, and pass through exceptions when available. Ensure disposal detaches callbacks and releases manager references. Add tests for the mapping policy and lifecycle where the Unity runtime permits; otherwise isolate the callback translation so it can be unit tested without loading the engine. Document supported Unity versions and callback-thread expectations. Complete evaluation and a local initial commit, create the GitHub repository under `WorkesLibraries`, and do not push.
